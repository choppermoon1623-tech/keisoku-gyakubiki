## ⓪「もんだいをみつける」タブ（2026-09-20 追加）

**①〜⑥は、やりたいことが決まっている生徒の道具でした。**
⑤ですら「テーマ・自分の案・行きづまり」を書けることが前提で、
そこが空白の生徒には1行も助けになっていませんでした。⓪はそこを埋めます。

### 考え方

逆引きの心臓部は「**生徒は装置名を知らないから調べられない → やりたいことの言いかえ語を持たせる**」でした。
その相似形がこれです。

> **生徒は「問題」という言葉が何を指すのか分からないから見つけられない。
> → 問題の『型』と『困りごとの言い方』を持たせる。**

問題は思いつくものではなく、**気づく**もの。だから「考えなさい」ではなく「見分けられるようにする」道具にしてあります。

### 束はひとつ、入口は3つ

| 生徒の状態 | 入口 | やること |
|---|---|---|
| なんにも浮かばない | あるある判定 | カードを1枚ずつ見て `ある／たまに／ない` を押すだけ。**えらぶのは、考えつくよりずっと簡単** |
| 場所なら言える | 場所からさがす | 13か所から選ぶと、そこで起きがちなことが出る。**観察シート（A4）を印刷して持ち帰れる** |
| 作りたい物はある | 逆算 | 「自動ドアを作りたい」→ だれが何に困っているのかへ戻す。**いちばん多い間違った入口を正す道** |

3つとも、同じカードの束（`var TANE`、77枚）を別の引き方で引いているだけです。
作る量が 1/3 で済み、質の管理点もひとつになります。

### 北海道ならではの困りごと（2026-09-20 追加・17枚）

**冬・雪（10枚）** 玄関前の雪／水道管の凍結／路面の凍結／落雪・つらら／灯油切れ／結露／除雪車／
物置の屋根の雪／雪かきの見きわめ／冬の換気わすれ

**動物・生き物（7枚）** クマの出没／林のそばでクマに近づく／畑のシカ・キツネ／カラスとゴミステーション／
電気さく／犬が庭から出る／牛舎の夜の見回り

引きかたを2つ足しました。**`冬・雪` と `動物・生き物` は場所ではないので**、
場所の並びのうしろに置き、見出しを「どこ・**どんなとき**」に直しています。

**★北海道のカードにも、必ず場所のタグを付けてあります。**
「通学路」を選んでもクマのカードが出る、というのが肝で、
`冬・雪` を選ばなかった生徒が、北海道ならではの困りごとに出会えないと意味がありません
（検査で、場所タグの無いカードが無いことを見ています）。

雪と動物が**この教材によく合う**のは、どちらも既存の51種でそのまま解けるからです。

| 困りごと | 何が分かれば | 装置 |
|---|---|---|
| 玄関前にどれだけ積もったか | 雪がどれくらい積もったか | 光距離センサ（雪面までの距離） |
| 水道管の凍結・路面の凍結 | 水道管／地面の温度 | 温度センサ（0℃が そのまましきい値になる） |
| 灯油切れ・屋根の雪 | 灯油／雪の重さ | 重さセンサ |
| クマがいまどこにいるか | そこに何かいるか | カメラAI画像センサ |
| シカ・カラスが近づいた | 近づいてきたか | 人感センサ／通過センサ |

**0℃という はっきりしたしきい値があるのが、雪・氷の題材の強み**です。
⑤の「しきい値の決め方が分からない」でいちばん つまずくところを、
「こおるかどうか」なら生徒が自分で説明できます。

### 困りごとの10の型（`var KATA`）

型はそのままセンサの種類に写ります。**センサ以前の話をしているのに、着地点がセンサになる**のがしかけです。

わすれる／見ていないと分からない／ずっと見ていられない／ちょうどよくできない／気づくのが遅い／
手がふさがる・届かない／人によってばらつく／危ない・ぶつかる／数える・記録が面倒／遠くのことが分からない

あるある判定では「ある」を押した型のかたよりを出します
（「あなたは “あとで気づいて困る” ことに気づきやすい人みたいです」）。ここで自分ごとに変わります。

### 3つの関門

「勉強したくない」「お金がない」で止まる生徒を、ここで拾います。学習指導要領の「課題の設定」そのものなので、**関門自体が教材**です。

1. **目や耳で分かる変化があるか** ―― `var MUZU`（16語）に当たったら言いかえの道を出す
2. **いつも同じルールでよいか** ―― 「そのつど人が考えて決める」を選ぶと注意が出る
3. **知らせる／動かす のどちらで楽になるか** ―― ④の「動作」につながる

**★1は止めません。言いかえを出すだけです。** 辞書は必ず外すので、止めると作業が死にます。

| 生徒が書いた | 出すもの |
|---|---|
| 片づけが苦手 | 「苦手」は測れないけど、**出しっぱなしに気づかない**なら測れる |
| 勉強したくない | そのとき何が起きていて いやなのか（暑い・うるさい・くらい） |
| ねむい | 部屋の空気がわるい／部屋が暑い／朝おきられない |

この言いかえ表が**⓪の第二の資産**です（①の言いかえ語、⑤の活用形に続く3つめ）。

### 出口 ―― もんだいの文

> 〔だれ〕が、〔いつ・どこで〕、〔何に〕こまっている。
> これは「〔型〕」なので、〔何〕が分かれば助かるかもしれない。

最後の〔何〕を、そのまま**①の検索欄に流します**（既存の検索エンジンがそのまま動く）。
④のテーマ欄、⑤の相談カード（`gkind='idea'`）にも渡せます。

**★⓪は独自のカード形式を作っていません。** AIに見てもらう経路は⑤の相談カード1本のまま。
「2つの形式をコピペで行き来させると、どちらの利用者にも意味不明になる」を繰り返さないためです。

### 設計上の決めごと

- **束を一覧では見せない。** 毎回ちがう順で12枚ずつ。全部ならべるとクラス全員が同じテーマを選び、借り物になる
- **カードに解決策も装置名も書かない。** 困りごとだけ（`test_mitsukeru.js` で装置名が混ざっていないか検査している）
- **`hint`（何が分かれば助かるか）を生徒に見せない。** 「わからない」を**2回**押したときだけ例を出す。
  1回目は考え方だけ。ここを最初から見せると、課題の設定そのものを肩代わりしてしまう
- **⓪に検索欄と装置パネルを出さない。** 装置から考えさせないため
  （検索欄・装置パネルで2回踏んだ「タブの外に置いたものは自分で消さないと出たままになる」を、今回は先に決めてから置いた）
- **生徒側にAIは入れない。** ⑤と同じ。テーマが決まらない生徒は⑤の「テーマや案が思いつかない」で⑥へ
- **「これにする」でカードを選びなおすと、「何が分かれば」は消す。**
  こまりごとが変わったのに古い答えが残ると、ちがう問題に前の答えが付いたまま①や⑤へ出ていく
- **開くタブ**：まだ何も書いていない端末は⓪、書き始めている端末は①（`m0Started()`）

### 印刷

- **観察シート（A4）** ―― 場所を選んで「観察シートを印刷する」。数日持ち帰って見てくる用。
  `body.printsheet` を付けて、画面のものを全部どける。**シートにも答え（hint）は出しません**
- **もんだいカード** ―― ⓪を開いたまま「印刷する」

### 文末の「か」―― ①の検索に見つかった欠陥

⓪のカードの `hint` を60枚ぶん①に通したところ、**1位が見当ちがいのものが10枚以上**ありました。原因はこれです。

> 生徒は「人が近づいた**か**」と文末に「か」を付けて書くが、
> 言いかえ語は「近づいた**ら**」の形で登録してある。
> **この一文字だけで語句の一致が全部外れ、代わりに説明文へのまぐれ当たりが1位を取る。**

⑤で踏んだ「活用形で一致しない」と同じ型が、こんどは**文末**で出たものです。`qTail()` で直しました。

- 「人が近づいたか」→ ~~磁気スイッチセンサ~~ → **人感センサ**
- 「ペットが動いたか」→ ~~水位センサ~~ → 加速度センサ

**★削るのは打ちこまれた言葉の側だけ。索引（言いかえ語）からは削りません。**
言いかえ語の「か」を削ると「ほか」「なか」まで変わってしまいます。
**短い言葉（4文字以下）にも掛けません**（「しずか」が「しず」になってマイクが消える）。

あわせて `年月日・時刻` に「何分・何秒・たった・経過」、`加速度センサ` に「動いた・動く・ふるえ」を足しました。
`eval_search.js` は 105/106・53/55 のまま、`eval_stuck.js` も 32/33 のままです。

## ⑤「行きづまったら」タブ

**別アプリ「AIおたずね箱」の、書かせる形をここに持ち込んだものです。**
AIも通信も使いません。ヒントはこのHTMLの中だけで組み立てています。

生徒に書かせるのは4つ（うち3つと「困っていること」は必須で、埋めないと**ボタンが押せません**）。

- テーマ・課題（何を解決しようとしている？）
- 条件・きまり（使える日数・お金・学校にある装置など）※任意
- 自分が考えた案・ためしたこと
- どこで行きづまったか
- いま、いちばん困っているのはどれ？（案が出ない／装置が分からない／しきい値／つなぎ方／動かない）

押すと、次の4つを返します。

1. **書いた言葉から見つかった装置** ―― ①と同じ検索エンジンに、書いた4欄を通したもの
2. **いま、確かめたいこと** ―― 足りていないところの指摘（下記）
3. **困っていることへのヒント** ―― 選んだ5種類に対応した定型
4. **近いかもしれない授業の例** ―― 見つかった装置を使っている実践

### 足りていないところの指摘

| 状態 | 返すこと |
|---|---|
| センサだけ見つかった | 気づいたあと何をするかが未定。伝える相手で手段が変わる |
| アクション装置だけ | 何が分かれば動かしてよいかが未定 |
| 両方見つかった | 次はしきい値と止め方 |
| どちらも出ない | 「そのときのようす」で書き直すよう促す |
| 条件・きまりが空 | 日数・お金・手持ちの装置を書くと案がしぼれる |
| ④設計メモが空 | 仮でよいので入れたほうが進む（候補から直接入る） |

### 自信が無いときは、候補を出さない

いちばん大事にした方針です。**まちがった装置を自信たっぷりに出すより、出さないほうがよい。**
出せないこと自体が「ようすを具体的に書こう」という指導になります。
実際、「話し合いがうまくいかない」のような装置の話でない相談には、候補をひとつも出しません。

### ①の検索をそのまま使えなかった理由

①は短い言葉（「くらい」「火事」）向けの調整です。⑤には長い文が来るので、そのまま通すと的外れなものが並びました。
⑤専用に `scoreLong()` を足し、次の2つを直しています。

- **説明文へのまぐれ当たりを減らす**。長文だと、ありふれた2文字の一致が積み上がって順位を奪う。
  名前・言いかえ語に当たったときを重くし、説明文だけの一致は軽くした
- **ひらがなだけの2文字の言いかえ語を使わない**。
  「どうやってドアが開いたの**どう**して」の「のど」が加湿器に当たっていた。
  一方「暑い」「火事」「教室」のような**漢字を含む2文字は、逆に強い手がかり**なので残してある

テストで見つかった語彙の穴も埋めました（「暑い」「寒い」が漢字だとどこにも当たらなかった／
「電気をつける」がスマートプラグに当たらなかった）。

### 的外れな候補が並んでいたのを直した（2026-09-19）

「ヒントを出しても的外れ」という指摘から調べたところ、**3つの欠陥が重なっていました。**
生徒が書きそうな11通りで採点する `tools/eval_stuck.js` を作り、**28/33 → 32/33** まで直しています。
①の検索（105/106・53/55）は変えていません。

**(1) 活用形で一致しない**

言いかえ語は辞書の形（「通る」「暗い」）で書いてあるのに、生徒は「通っ**たら**」「暗く**て**」と書きます。
文字列の一致なので、一文字も当たりませんでした。
「人が通ったら電気をつける」と書いても**人感センサが出てこない**のはこれが原因です。

語幹だけ（「通」）にすると「交通」「通学」にまで当たるので、**ありうる語尾に置きかえた形**を
あらかじめ作って持たせました（`CONJ` → `v.phv`）。⑤の長い文でだけ使い、①の短い検索では使いません。

| | 前 | 後 |
|---|---|---|
| 人感センサ（「人が通ったら」） | 15.6点・4位以下 | 33.6点・候補に出る |

**(2) 行きづまり欄に、いちばん強い重みがかかっていた**

`GW` の重みが `テーマ1.0 / 条件0.6 / 案1.2 / 行きづまり1.4` でした。
けれど**装置の手がかりが書いてあるのはテーマと案**で、行きづまり欄は困りごとの記述
（「昼も反応してしまう」「分からない」）です。ここを重くしていたせいで、
**困りごとの言い回しにたまたま一致した装置が1位に居座って**いました。

> 「夜だけ動かしたいのに、昼も反応してしまう」の「**夜だけ**」が
> 年月日・時刻の言いかえ語にそのまま入っていて、44.8点の一撃で1位。
> 生徒が書いた「人が通ったら」の人感センサを押しのけていた。

重みを `テーマ1.2 / 条件0.5 / 案1.4 / 行きづまり0.8` に入れ替えました。

**(3) 場所の言葉で、関係ない装置が付いてきた**

「**教室**の西日がまぶしい」の「教室」がCO2センサの言いかえ語に当たり、
**教室の話すべてにCO2センサ**が付いてきていました。
場所は「どこでの話か」を言っているだけで、何を測るかを決めません。

**AIおたずね箱と同じ Firebase プロジェクト（`ai-otazune`）の、同じ `otazune` コレクションを使います。**
だから先生は受付を1つ持てば、**おたずね箱の相談と計測・制御の相談を、同じGoogleアカウントで**見られます。

- **`firestore.rules` は変えていません。** おたずね箱のルールは `kind` と `fields` の中身を

- 逆引きが出した装置の候補（`sens` / `acts`）も一緒に送るので、先生の画面で選び直す手間がありません

### 生徒側（⑤）

- **受付コードを入れたときだけ**送信欄が働きます。コードが無ければ、このページは**これまでどおり通信しません**
- コードは `keisoku-gyakubiki-code` に覚えるので、**次の時間もそのまま答えを見られます**
- 見えるのは**自分が出した分だけ**。ほかの人の相談は、ルールで読めません
- 先生がまだ見ていない（`new`）うちは、生徒が自分で取り消せます
- 状態が生徒にも見えます ―― 先生が見るのを待っています／先生が見ています／答えが返ってきました／見送り

> **ブラウザのデータを消すと匿名IDが変わり、自分が出した相談も見えなくなります。**
> 大事な答えは印刷しておくこと（答えの枠は印刷に残るようにしてあります）。

### 先生側（⑥）

Googleでログインして「受付をつくる」。**6文字のコード**が出るので、生徒に伝えます
（まぎらわしい `I O 0 1` を外した32文字から選びます）。

- 受付は**開く／閉じる**を切りかえられます。閉じると新しい相談は来ませんが、返した答えは生徒に見えたままです
- 届いた相談をひらくと、これまでと同じフォームに入ります。答えを書いて「**生徒に返す**」
- 「対応中にする」「見送りにする」も生徒の画面に出ます
- **生徒の画面に出る前に、かならず確認が入ります。** 一文字打つたびに書きこむことはしません
  （読んでいる途中で内容が変わってしまうため、返すときにだけ書きこみます）

### ここを外すと壊れる

**Firestore のルールはフィルタではありません。** 「権限のある文書だけ返す」ということをせず、
権限の無い文書が混じり**うる**クエリは丸ごと拒否されます。おたずね箱で一度これにやられています。

- 先生の購読には `where("ownerUid","==",自分)` が要る（`fbq.watchReqs`）
- 生徒の購読には `where("authorUid","==",自分)` が要る（`fbq.watchMine`）

どちらか片方でも外すと、**一覧が permission-denied で空になります。**

## ⑥ 先生用 ―― まとめてAIにかける

先生は**自分の端末で**このタブを開きます。
クラウドで受け取る（上）と、貼りこんで受け取る（下）の**どちらでも同じフォームに入ります**。

### 1. 受け取る

集めた相談カードを、**何人分でもまとめて**貼って「読みこむ」。
`━━ 計測・制御 相談カード ━━` で区切って読むので、メールやドキュメントに並んでいても通ります。
生徒が口頭で相談してきたときは「白紙で1件つくる」で先生が直接書けます。

### 2. 相談の一覧

この端末に保存されます（`keisoku-gyakubiki-soudan`）。「未」「返した」で管理できます。

### 3. AIにかける

1件ひらくと、**欄ごとに分かれたフォーム**になります。先生がその場で直せます。

- **答え方の方針**を1件ごとに切りかえ。生徒が選んだ「いま困っていること」に合わせて既定が決まる

  | 生徒の困りごと | 既定の方針 | 何をする方針か |
  |---|---|---|
  | テーマや案が思いつかない | しっかり説明する | 用語も定義から説明してよい。ただし完成品は書かない |
  | どの装置を使えばいいか | 事実と確かめ方 | 確かなことと、はっきりしないことを分けて示す |
  | しきい値の決め方 | **ヒント中心** | 答えは書かない。道すじと着目点だけ |
  | つなぎ方・プログラム | 事実と確かめ方 | どの配布資料を見ればよいかを示す |
  | 作ったが動かない | **ヒント中心** | 切り分けの手順だけを示す |

- **AIに送る文は自動で組み上がり、畳んであります。**フォームを直すたびに作り直されます。
  開いて直接書きかえてから送ることもできます
- **「送る文をコピー」だけでも使えます**（APIキー不要・無料）。ふだん使っているClaudeやChatGPTに貼るだけ
- APIキーを入れると「🤖 AIに聞く」が出て、この画面から直接聞けます（ストリーミング表示）
- 答えは**編集できる欄**に出ます。直してからコピーするか、印刷して生徒に渡します

送る文には、次のものが自動で入ります。

1. その生徒が書いた内容と、困っていること
2. 逆引きが出した候補と、その**資料のファイル名**
3. **この学校で使える51種の装置の一覧**
4. 石川研究室サイトのURL

**3がこの仕組みの肝です。**ふつうにAIに聞くと、学校に無い部品を平気ですすめてきます。
「この一覧の中から」と縛ると、返ってくる案がそのまま授業で成立します。

あわせてAIには、つなぎ方・コネクタ番号・しきい値の数値は**書かない**（石川研究室の配布資料で
生徒が確かめる決まりなので推測させない）、そのまま提出できる完成品は書かない、
生徒がすでに考えた案を伸ばす方向で書く、を指示してあります。

### APIキーの置き場所

**既定は「このタブだけ」**（`sessionStorage`）。タブを閉じると消えます。
共用のパソコンではこの既定のまま使ってください。自分専用の端末なら「この端末に保存」に切りかえられます。

## 受付コードごとの装置共有（2026-09-20）

**この索引に載っている51種が、その学校に全部あるとはかぎりません。**
「学校にある装置と決めつけない」（下の2）の続きとして、
**先生がクラスごとに「使える／相談／使えない」を設定し、生徒の画面に配る**しくみを足しました。

### 先生（⑥）

ログインして受付を開くと「○○で使える装置」が出ます。
装置ごとに **使える／先生に相談／使えない** を選び、「装置の状態を保存」。未設定は**未確認**です。
使えるものだけ先に設定して「未確認の装置を『使えない』にする」でまとめて埋められます。

- 受付を切りかえると対象クラスも変わる。未保存があれば確認が出る
- 同じ受付を複数のタブで編集した場合、**最後に保存したものが残る**（履歴は持っていません）

### 生徒（①④⑤）

画面上の「この授業で使える装置」に受付コードを入れます。**⑤の「先生に送る」と同じコード**です。
コードを入れると匿名認証と受付の読み取りが走りますが、**相談文は「先生に送る」を押すまで送りません。**

- 先生が保存すると、つないでいる生徒の画面がその場で変わります
- **「使えない」は①の一覧と⑤の候補から消えます**（①はチェックを入れれば見られます）
- **「使える」→「相談」→「未確認」の順に並びます。ただし並べ替えであって、選抜ではありません**
- ④の設計メモは消さずに、いま選んでいる装置の状態を出します
- すでに出したヒントは、装置が変わったら押し直すよう案内します
- 未接続・未設定を「使える」とは**扱いません**
- 通信が切れた・キャッシュしか見えないときは、その旨を出します

> **「使える」は台数・貸出予約・配線の互換性を保証しません。** 画面にもそう書いてあります。

### AI相談への反映

先生が選んでいる受付の**全装置の状態**を、AIへの指示文の末尾に付けます。
「使えない」は提案しない、「相談」「未確認」は先生への確認を条件にする、と指示します。
コピー時・API送信時に現在の状態へ差し替えます。**答えを先生が確かめるのは、これまでどおりです。**

### 置き場所 ―― ルールは変えていない

既存の `otazune/{受付コード}` に、`updateDoc` で1フィールド足すだけです。

```js
equipment: {
  v: 1,
  states: { "s-hikari": "yes", "s-jinkan": "ask" },   // DEV の id
  updatedAt: 1234567890000                            // 保存した端末の時計
}
```

状態は `yes` / `ask` / `no`。**欠けていても壊れた値でも「未確認」として読みます。**

おたずね箱のルールは、受付の `update` に `hasOnly` を**かけていない**（持ち主かどうかだけ見る）ので、
**ルールファイルは変えていません。** ただし **`create` には `hasOnly` があります。**

> **受付を新しく作るときに `equipment` を一緒に書いてはいけません。** create が丸ごと拒否されます。
> 作るのは既存のキーだけ、装置は作ったあとに `updateDoc` で足す ―― この順番を崩さないこと。

受付の保存（`saveRoom`）は `setDoc(..., {merge:true})` なので、
おたずね箱側で受付名を直しても**装置の設定は消えません**。
`tools/test_stuck.js` に、この2つ（`updateDoc` で書く／`merge` で保存する）をソースの上で固定する検査を入れてあります。

### 引き継いだあとに直した2点

Codex の実装を引き継いで検査したところ、2つ直しました。

**1. 装置パネルが6タブ全部に出ていた。**
下の「3. 検索欄」とまったく同じ話で、**タブの外に置いた操作は自分で消さないと出たままになります。**
②授業の例・③進め方には装置の一覧が無く、⑥先生用には先生の編集欄があるのに、
生徒向けの「この授業で使える装置」と「使えない装置も表示」が上に出ていました。
さらに⑤では、**受付コードの入力欄が上下に2つ並んで**いました。
①④⑤だけに出し、⑤では下の「先生に送る」の欄に誘導します。

**2. 装置の状態が、並べ替えではなく選抜になっていた。**
`eqOrder()` が `slice(0,3)` の**前**に走っていたため、
関連の薄い「使える」装置が、関連の濃い装置を押し出していました。

| 関連度 | 装置 | 状態 |
|---|---|---|
| 67.8 | 光センサ | 未確認 |
| 48.0 | 明るさセンサ（内蔵） | 未確認 |
| 39.2 | **人感センサ** | 未確認 |
| 30.8 | 通過センサ（レーザ） | **使える** |

この状態で出ていたのは「通過センサ／光センサ/明るさセンサ」。
生徒が**「人が通ったら」と書いているのに人感センサが消え**、4位の通過センサが1位になっていました。
**出す3つは関連の濃さで選び、その3つの中を状態で並べる**ように直しています。
`使えない` は `eqAllowed` で先に外してあるので、除外はこれまでどおり効きます。

## レビューで直した5点（2026-09-20）

### 1. CO2・煙／異臭 ―― 実測と模擬実験を分ける

カードの中で言っていることが食いちがっていました。

| | もとの書き方 |
|---|---|
| CO2の説明 | 「二酸化炭素の濃度を**調べ**、換気を考える手がかりにする」 |
| CO2の注意 | 「アルコールセンサでCO2濃度は**測れない**」 |
| CO2の資料注記 | 「CO2そのもののセンサは無く、アルコールセンサで**代用します**」 |
| アルコールセンサの注意 | 「CO2や煙の濃度を測る**代用品ではない**」 |

説明と注意が正面から矛盾し、さらに「代用します」と「代用品ではない」が食いちがっていました。
煙のほうも「検知できる対象は**機種による**」と書いてあり、実在する煙センサから選べるように読めました。

**「代用（measurement substitute）」をやめ、「模擬（simulation）」と言い分けました。**
アルコールセンサは *CO2の代わりに濃度を測る装置* ではなく、
*知らせる流れを試すための入力役* です。

- 名前を **CO2センサ（模擬）** / **煙・異臭センサ（模擬）** に変更
- `sim` という項目を足し、**模擬実験のバッジ**と「何が測れないか」の一行を出す
- 説明は「測るセンサは資料にはない」から始める。使用例も「模擬実験で確かめる」に
- 注意は「レポートには必ず『模擬実験』と書く」「何を測れていないかを説明する」まで書く
- 資料注記から「代用します」を削除。アルコールセンサの「代用品ではない」はそのまま
- AIに渡す装置一覧にも `〔実測できません：…〕` を付ける。付けないとAIが濃度を測れる前提で書いてくる

**炎センサはそのまま**です。あちらは資料に専用ページがあり実測できるので、
「実際の火災警報器の代わりにはしない」という注意だけで筋が通っています。
実測できるもの（炎）と模擬（CO2・煙）の対比が、そのまま教材になります。

### 2. 掲載装置を「学校にある装置」と決めつけない

AIに渡す文が **「この学校で使える装置（これ以外は提案しない）」** と書いていました。
この索引は石川研究室の**資料**をもとにしたもので、**その学校に実物があるかは確かめていません。**
このままだと、生徒が手に入らないものを設計してしまいます。

- 見出しを **「この教材で扱う装置（これ以外は提案しない／実物の有無は教師が確認）」** に
- 「一覧にあっても、その学校に実物があるとはかぎりません（確認するのは教師です）」を明記
- 「『学校にあります』と断定せず、『この一覧にあります』と書く」よう指示
- 「手に入らなかったときのために、できれば代わりの案も1つ」を追加

**一覧の外を出さないことと、一覧の中が必ずあることは別の話**です。前者の縛りは残してあります。

### 3. 検索欄は「さがす」タブでだけ出す

検索欄は `<header>` の中にあり、**どのタブでも出たまま**でした。
②〜⑥では結果の一覧（`#list`）が隠れているので、打ちこんでも何も起きません。
**「検索が壊れている」と見える最大の原因**がこれでした。`showTab()` で出し分けます。

### 4. 保存メモの「更新」と「別案として保存」を分ける

「読み戻して編集」して保存すると、**毎回1件増えていました**（画面にも
「新しい設計として追加されます」と書いてあり、直っていない状態が既知のまま残っていました）。
直したあと少し書き足すたびに、ほとんど同じメモが並びます。

- 保存メモに **`id`** を持たせる（`unshift` で積むので、添字は並べ替えでずれる）
- 読み戻している間は **「この設計を更新する」**。**「別案として保存する」**が別ボタンで出る
- 「入力をクリア」「削除」で更新先を外す。編集中のものは一覧で枠が付く
- **前からある保存メモは、読みこむときに `id` を足して書きもどすので、そのまま引き継がれます**

### 5. 受付コードを打ちかえたときの競合（クラウド）

`cCheck()` は **「確認中なら新しい入力を無視する」**形でした。
1つめを確かめている最中に打ちかえると、2つめは調べられないまま、
**画面には2つめが見えているのに、つながっているのは1つめ**になります。
そのまま送ると、**別のクラスの受付に相談が入ります。**

再現すると、入力欄が `74U399`（受付B）なのに送り先は `Y6ZTK7`（受付A）でした。

- 呼び出しごとに番号（`cSeq`）を振り、**いちばん新しい呼び出し以外の応答は捨てる**
- コードを消したとき・忘れたときも番号を進めて、飛んでいる応答を無効にする
- 購読（`cWatchMine`）も、見はじめたときのコードと変わっていたら通知を捨てる
- 打ちかえた瞬間に**いったん送れなくする**。確認が終わるまで送信ボタンは押せない
- 送信ボタンの条件に「**入力欄のコード＝つながっている受付**」を追加。押した時点の受付に固定して送る

### おまけ ―― 索引の区切り

1の書き直しで、装置の話でない相談にCO2が出るようになりました。調べると
**前からあった欠陥**で、`y` と `k` の配列を**区切りなしで連結**していたため、
語と語の**境目に、どこにも書いていない2文字**ができていました。

- 「息苦しい」＋「いきぐるしい」の境目に **「いい」** → 「どうやって決めれば**いい**か」に一致
- 「まどを開けるタイミング」の中の **「みん」** → 「**みん**なの意見」に一致

`'|'` を区切りに入れて、2文字が境目をまたげないようにしました。
①の成績は変わらず（105/106・53/55）、出てくる件数だけ減りました（平均4.7→4.4件）。

## 検索のしくみ（授業で効くポイント）

生徒は装置名を知らないので、**必ず自分の言葉で入力してくる**（「暗くなったら」「土がかわいたら」「音を出さずに知らせたい」）。
そこで単純な部分一致ではなく、次を組み合わせています。

1. 各装置に「生徒が言いそうな言い方」を登録（いまは1台あたり10〜25語）
2. 入力文を2文字ずつに切って照合（文のままでも引ける）
3. 「〜たら」「〜したい」など、どの装置にも出てくる語尾は自動的に無視
4. **索引を強さの順に分ける**（下記）
5. **計測と制御を別の列にして、それぞれの中で順位をつける**（下記）

### 索引を強さの順に分ける

`v.nm`（装置名）＞ `v.hi`（言いかえ語・検索語）＞ `v.all`（説明文）＞ `v.ct`（カテゴリ）。

**もとは、この4つを全部ひとつの索引に混ぜていました。**そのせいで、カテゴリ名にある言葉を打つと、
そのカテゴリの装置が全員同じだけ加点され、本人がうもれていました。

- 「音」→ カテゴリ「動き・かたむき・音」の加速度センサが1位、**マイクは3位**
- 「天気」→ カテゴリ「水・天気」の全員が同点
- 「きょり」「障害物」→ カテゴリ「きょり・通過・障害物」の全員が同点

カテゴリは弱い加点（+10）にとどめ、決め手にしないようにしてあります。

### 計測と制御を別の列にする

混ぜて順位をつけていたので、片方が強いと、もう片方が丸ごと消えていました。

- 「音」→ 名前に「音」がつく出力装置が上位を占め、マイクが押し下げられる
- 「こえでうごかす」→ 「うごかす」を共有するモータ3台で埋まり、音声認識が候補から落ちる

いまは `searchType()` が種類ごとに順位をつけ、**1位との差で切り捨てるのも種類の中だけ**で行います。
当たりの強いほうの列を先に見せるので、「まわす」なら制御が先、「暗い」なら計測が先に出ます。

### 実測

`node tools/eval_search.js` で測れます。

| 問題集 | 列の中で1位 | 列の中で3位以内 | 1回あたりの表示 |
|---|---|---|---|
| 調整に使った106問 | 99% | 100% | 2.9件 |
| **別問題集55問** | **96%** | **96%** | 4.7件 |

**下の段が実力に近い数字です。**上は調整しながら見ていた問題集なので甘くなります。
別問題集は、言いかえ語を足す*前*に作って、足し終えてから一度だけ使いました。

直す前の数字は、同じ別問題集で**1位60%・3位以内76%**でした。上がったぶんの大半は、
採点式ではなく**言いかえ語を足したこと**（y+37語・k+292語）で説明がつきます。
**逆引きの質は、ほぼ言いかえ語の量で決まります。**

試した中で、効かなかったもの（測ってから捨てました）。

- **動詞の活用形を自動生成する**（「おす」→「おし」）。雑音のほうが増えた
- **言いかえ語をめずらしさで重みづけする**。わずかに下がった

### 分かっている外し

- 「おしたらうごく」→ 押しボタンセンサが出ない（「ボタンをおしたら」なら出る）
- 「こえでうごかす」→ 音声認識判別が列の3位以内に入らない
- 「ふるえて知らせたい」→ 振動モータでなく加速度センサが先に出る

どれも「登録してある形と、打たれた形がずれている」ことが原因です。
困る場面に出会ったら、`var DEV` のその装置に、打たれた言い方をそのまま足してください。

## 印刷

各タブを開いた状態で「印刷」すると、そのタブの内容が印刷されます。

- ①で何も絞り込まずに印刷 → **全51種の装置一覧**（教室掲示・配布用）
- ④で印刷 → 生徒の設計メモ（ワークシートに貼る）

  **行きづまった生徒が先生に見せる紙**として使えます（何を考えてどこで止まったかが全部のっている）

## データを直すには

`index.html` 内の `var DEV = [...]` を編集します。1件の書式：

```js
{id:'s-hikari', t:'s', c:'光・色', n:'光センサ',
 d:'何ができるか（1〜2行）',
 y:['暗くなったら','夜になったら'],   // 生徒が言いそうな言い方＝逆引きの入口
 k:['ひかり','あかるさ','照明'],      // 検索用のことば（かな・漢字の両方あると強い）
 u:'使いどころ',                      // 💡 の行
 w:'注意すること'}                    // ⚠ の行（なければ省略可）
```

- `t` は `'s'`＝センサ（計測）／`'a'`＝アクション装置（制御）
- `b:1` を足すと「micro:bit内蔵」バッジがつきます
- 学校にある装置だけに絞りたいときは、不要な行を消せばそのまま動きます

授業例は `var EXAMPLES`、進め方は `var STEPS`、ヒントは `var TIPS` です。

**検索が当たらないときは、まず `y` と `k` を足してください。**採点式をいじるより確実です。
漢字・ひらがな・ふだんの言いまわしの3方向から足すと効きます
（「暑い」と「あつい」、「転んだ」と「ころんだ」、「水を出したい」と「みずをだす」）。
足したら `node tools/eval_search.js` で、ほかが崩れていないか見ます。

## 保存データ

設計メモはブラウザの localStorage（そのパソコンの中だけ）に保存されます。外部には一切送信しません。
共用パソコンでは、次の生徒が使う前に④タブで削除させてください。

⓪に書いた内容は `keisoku-gyakubiki-mitsukeru` に残ります（選んだカード・型・もんだいの文）。
消すときは⓪の「書いたものを消す」。

⑤に書いた内容も同じく localStorage に残ります（キーは `keisoku-gyakubiki-stuck`）。
次の時間に続きを書けるようにするためです。消すときは⑤の「書いたものを消す」。

⑥で**貼りこんで**受け取った相談は `keisoku-gyakubiki-soudan` に、**先生の端末だけに**残ります。

**⑤から「先生に送る」で送ったものだけが、クラウド（Firestore）に出ます。**
受付コードを入れていなければ、このページはどこにも通信しません。
クラウドに出るのは、生徒が書いた4つの欄・困っていること・逆引きが出した候補・**なまえ**です。
氏名を出したくないときは、⑤の「なまえ・出席番号」に出席番号だけ書かせてください。
受付コードそのものが合言葉なので、**コードは口頭・黒板・Classroomでだけ配ること。**

Googleログインのポップアップ、承認済みドメイン、実際のAI応答の中身も同じです。

### 直したことを確かめるやり方

**新しい検査を、直す前のコードにぶつけて落ちることを見てから**直しています。

- ⑤ 入力欄は `74U399`（受付B）なのに、送り先が `Y6ZTK7`（受付A）になる

エラーの言い方（401／429／AIが断ったとき）まで検査しています。

あわせて「**生徒の画面にAIへの指示文が出ていないこと**」も確かめています。
